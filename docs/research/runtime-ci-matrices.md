## What the evidence says

**A three-browser Playwright matrix is not normal for a non-DOM agent library.** None of these four official repositories runs its portable core across Chromium, Firefox, and WebKit. The two AI libraries with Playwright coverage—Vercel AI SDK and TanStack AI—install and run **Chromium only**, and their Playwright suites primarily exercise RSC/application UI behavior rather than re-running the non-DOM core conformance suite in each engine. Effect and Hono use `happy-dom` or JSDOM for browser-adjacent packages and have no real-browser engine matrix.

That does **not** make a broad browser claim self-proving. The comparison also shows substantial claim/CI gaps:

- Effect ships an official Bun package but its checked CI workflow tests only Node and Deno.
- Vercel documents Deno and browser support, but its core CI substitutes an edge VM and a browser bundle check for native Deno/browser execution.
- TanStack AI says its core works anywhere, while CI is Node-centric plus Chromium application E2E and one targeted workerd regression.
- Hono most closely aligns named server-runtime claims with native jobs: Node, Bun, Deno, workerd, Fastly, and Lambda variants. It does not use browser engines to prove a server-framework portability claim.

## Recommendation for Commissary

Commissary’s own portability decision promises Node.js 22+, Bun, Deno, modern browsers, and Cloudflare Workers, says workerd anchors edge CI, and says every advertised runtime family is exercised rather than treated as best effort ([ADR 0003](../adr/0003-keep-effect-behind-javascript-contracts.md#decision)). Match that unusually explicit contract rather than copying peers’ claim/coverage gaps:

1. **Use native runtime jobs as the release gate:** supported Node majors (at minimum Node 22 plus the newest supported major), current Bun, current Deno, and current workerd. Run a compact shared core conformance/smoke suite in each; do not count typechecking, bundling, `edge-runtime` VM, JSDOM, or `happy-dom` as substitutes.
2. **Add one real-browser core smoke target initially, preferably Chromium:** import the published artifact and exercise only browser-relevant Web Platform boundaries used by core (ESM loading, streams, `AbortSignal`, `crypto`, `fetch`/`Request`/`Response` as applicable). Keep UI and DOM testing out of core because Commissary is non-DOM.
3. **Do not make Chromium + Firefox + WebKit Playwright mandatory by default.** The primary-source comparison provides no precedent that this is standard for a non-DOM agent core. Add Firefox/WebKit when Commissary introduces engine-sensitive browser behavior, a browser-specific adapter, or an unqualified compatibility guarantee whose risk warrants engine-level proof.
4. **Label support precisely:** publish a small matrix that distinguishes native-tested, simulated, bundle-only, and untested. If the public wording remains “modern browsers,” say that Chromium is the maintained representative smoke target and that the core relies only on enumerated Web APIs; otherwise, a literal claim of all major browser engines should be backed by the three-engine matrix.

In short: **prioritize Node/Bun/Deno/workerd parity over three browser engines.** A single real-browser smoke test is proportionate for the current non-DOM core; the three-engine matrix is a deliberate stronger guarantee, not the ecosystem norm.
