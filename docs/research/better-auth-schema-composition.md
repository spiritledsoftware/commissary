# Better Auth schema composition

Research snapshot: 2026-08-03. The vendored checkout is Better Auth `1.6.25` at commit [`222facff556e6c570bbd6b7fd5923757b5a55711`](https://github.com/better-auth/better-auth/tree/222facff556e6c570bbd6b7fd5923757b5a55711) ([package metadata](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/better-auth/package.json#L1-L11)). This note describes that snapshot; it does not propose Commissary's final definition model.

## Short answer

Better Auth uses a small, ORM-independent **logical database schema** as the common input to runtime adapters, migration code, ORM source generators, and TypeScript inference. Core owns four logical model keys (`user`, `session`, `account`, and `verification`); plugins contribute the same table-and-field shape. A field carries a logical type plus behavioral and storage hints, while table and field aliases map the logical contract onto host naming. The effective schema is assembled from auth options and plugin schemas before an adapter sees it ([field and table contracts](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/type.ts#L164-L304), [plugin contract](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/plugin.ts#L1-L11), [composition](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/get-tables.ts#L4-L32)).

This is not ORM-schema inference. Better Auth generally projects its own logical schema **outward**. Drizzle generation writes a complete TypeScript schema from that projection; Prisma generation parses and augments an existing Prisma file; the built-in Kysely migrator introspects existing tables and columns and adds missing ones. At runtime, a host-supplied Drizzle schema object is a lookup/mapping target, not a source from which Better Auth reconstructs its logical field contract ([CLI dispatch](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/cli/src/generators/index.ts#L7-L40), [Drizzle lookup](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/drizzle-adapter/src/drizzle-adapter.ts#L115-L150), [Drizzle runtime schema resolution](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/drizzle-adapter/src/drizzle-adapter.ts#L153-L193)).

## 1. Declaration vocabulary

### Core and host-added fields

`DBFieldAttribute` has one required property, `type`, whose portable domain is `string`, `number`, `boolean`, `date`, `json`, string/number arrays, or a string-literal enum array. Optional attributes describe requiredness, response visibility, input permission, an application default, an update callback, transforms, Standard Schema validators, a single foreign-key reference, uniqueness, bigint storage, physical field name, sortability, and a single-column index hint ([type domain](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/type.ts#L164-L182), [field attributes](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/type.ts#L184-L282)).

Core declares its fields directly in `getAuthTables`. For example, `user.email` is required, unique, sortable, and renameable; `session.userId` is required, indexed, and references the canonical `user.id` schema key with cascading deletion. The canonical key is intentional: aliases are resolved downstream and must not become ambiguous schema keys ([user declarations](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/get-tables.ts#L170-L218), [session relation and alias rationale](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/get-tables.ts#L104-L168)). An `id` is implicit rather than present in each table's `fields`: the plugin documentation promises an ID for every table, and the Drizzle generator emits one according to the configured ID strategy ([official plugin schema documentation](https://www.better-auth.com/docs/concepts/plugins#schema), [Drizzle ID generation](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/cli/src/generators/drizzle.ts#L165-L188)).

Hosts customize a core model with `modelName`, a logical-to-physical `fields` rename map, and `additionalFields`; `id` is deliberately excluded from the latter two maps ([option type](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/types/init-options.ts#L148-L166)). The official database guide says logical names remain the TypeScript API names even when physical names differ, and documents `additionalFields` as the type-safe way to extend user and session responses and inputs ([official custom-table guidance](https://www.better-auth.com/docs/concepts/database#custom-tables), [official additional-field guidance](https://www.better-auth.com/docs/concepts/database#extending-core-schema)). Current source also merges `additionalFields` for account and verification, not only user and session ([all four merges](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/get-tables.ts#L61-L99), [account merge](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/get-tables.ts#L223-L310)).

`input`, `returned`, validation, transforms, and defaults are also runtime API semantics, not merely DDL hints. Input parsing rejects `input: false` values, runs synchronous Standard Schema validation and transforms, supplies defaults on creation, and checks required fields; output parsing omits `returned: false` fields ([runtime parsing](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/better-auth/src/db/schema.ts#L143-L213), [output field filtering](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/better-auth/src/db/schema.ts#L20-L65)). The official guide consequently treats `input` and `returned` as independent security controls ([official behavior table](https://www.better-auth.com/docs/concepts/database#extending-core-schema)).

### Plugin fields and tables

A plugin's `schema` is `Record<tableKey, { fields, modelName?, disableMigration? }>` using the same `DBFieldAttribute` shape ([plugin schema type](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/plugin.ts#L1-L11)). It may introduce a table or extend a core table simply by using `user`, `session`, `account`, or `verification` as its key. The official plugin guide documents both cases and states that plugin-added user/session fields flow into endpoint results and TypeScript inference ([official schema API](https://www.better-auth.com/docs/concepts/plugins#schema)). The built-in admin plugin is a compact real example: it contributes server-owned fields to `user` and `session`, marking every authority-bearing field `input: false` ([admin schema](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/better-auth/src/plugins/admin/schema.ts#L1-L40)).

Plugins expose two distinct override styles:

- The generic `InferOptionSchema`/`mergeSchema` path lets a host rename a plugin table and its declared fields. `mergeSchema` mutates only `modelName` and `fieldName`; it does not override type, requiredness, indexes, or relations ([override type](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/better-auth/src/types/plugins.ts#L14-L26), [merge implementation](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/better-auth/src/db/schema.ts#L280-L314)).
- Richer plugins may define their own option shape. Organization permits `additionalFields` on several plugin-owned models, then explicitly spreads those additions into its declared fields. It also declares field-level indexes and references in the same portable vocabulary ([organization option shape](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/better-auth/src/plugins/organization/types.ts#L292-L350), [organization assembly](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/better-auth/src/plugins/organization/organization.ts#L1052-L1197)).

`disableMigration` means “keep this table in the runtime schema but do not generate/migrate it.” Plugin composition translates the singular plugin property to the effective table's `disableMigrations`, and every examined generator/migrator skips such tables ([composition](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/get-tables.ts#L7-L31), [official opt-out example](https://www.better-auth.com/docs/concepts/plugins#schema), [Drizzle skip](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/cli/src/generators/drizzle.ts#L47-L53)). This is the main escape hatch for externally managed tables.

## 2. Composition and override behavior

`getAuthTables(options)` is the composition boundary:

1. Plugin schemas are reduced in plugin order. For a repeated table key, fields are object-spread and later plugins win on duplicate field keys; the latest truthy `modelName` wins; `disableMigration` uses the latest defined value ([reducer](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/get-tables.ts#L4-L32)).
2. Plugin contributions to the four core keys are extracted. Core field objects are created, then plugin fields, then host `additionalFields` are spread over them. Therefore, for DDL/effective adapter metadata, host additional fields win same-key collisions with plugin and core fields ([user precedence](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/get-tables.ts#L170-L218), [session precedence](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/get-tables.ts#L104-L168)).
3. Remaining plugin-owned tables are appended, with conditional session/verification/rate-limit tables determined by storage options ([final assembly](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/get-tables.ts#L313-L318)).

There is no collision diagnostic or namespaced ownership. A same-key spread silently replaces metadata. More importantly, request parsing recomposes fields differently: it starts from `getAuthTables` plus host additions and then spreads every plugin's fields again, so plugin fields win there ([runtime composition](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/better-auth/src/db/schema.ts#L20-L58)). Thus a collision can have host metadata in the generated/adapted database schema but plugin metadata in runtime input/output parsing. This is a concrete limit, not a safe extension mechanism.

## 3. How hosts generate or adapt ORM schemas

The CLI loads the Better Auth config, gets its initialized adapter (or a mock selected by `--adapter`/`--dialect`), and dispatches on adapter ID. Built-ins are Prisma, Drizzle, and Kysely; a custom adapter must expose `createSchema` ([generate command](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/cli/src/commands/generate.ts#L130-L165), [generator dispatch](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/cli/src/generators/index.ts#L7-L40)). The official CLI documentation accurately summarizes the intended split: generate ORM source for Prisma/Drizzle, or SQL for built-in Kysely; only Kysely supports direct `migrate` ([official CLI documentation](https://www.better-auth.com/docs/concepts/cli#generate), [official database migration scope](https://www.better-auth.com/docs/concepts/database#migrations)).

| --- | --- | --- |

### Existing Drizzle/user schemas

The Drizzle runtime adapter accepts a host schema object and provider. It uses `config.schema` or Drizzle's `db._.fullSchema`, then looks up the model name Better Auth resolved; absence is an initialization/query error ([adapter config and lookup](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/drizzle-adapter/src/drizzle-adapter.ts#L115-L150), [model lookup](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/drizzle-adapter/src/drizzle-adapter.ts#L179-L193)). On create it verifies that each outgoing logical field resolves to an actual Drizzle table property and gives a regenerate/update-schema error for a missing property ([field check](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/drizzle-adapter/src/drizzle-adapter.ts#L668-L691)).

The official Drizzle guide gives three host-controlled alignment mechanisms:

1. Alias an existing table object under the logical key, e.g. `{ ...schema, user: schema.users }`.
2. Set `user.modelName: "users"`, or set global `usePlural` when all table exports are plural.
3. Keep a logical Drizzle property such as `email` while changing its SQL column name to `email_address`, or set Better Auth's `user.fields.email` mapping explicitly.

These are documented in [Modifying Table Names](https://www.better-auth.com/docs/adapters/drizzle#modifying-table-names), [Modifying Field Names](https://www.better-auth.com/docs/adapters/drizzle#modifying-field-names), and [Using Plural Table Names](https://www.better-auth.com/docs/adapters/drizzle#using-plural-table-names). The resolver first tries the exact model/query key, optionally pluralizes, then can match a supplied schema table object back to Drizzle's full schema by object identity ([query-model resolution](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/drizzle-adapter/src/drizzle-adapter.ts#L693-L727)). None of these paths infer Better Auth field attributes, plugin contributions, or API types from an existing host table.

## 4. Indexes and relations

### Indexes

The portable schema exposes only `unique?: boolean` and `index?: boolean` on an individual field ([field contract](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/type.ts#L248-L278)). The Drizzle generator emits `.unique()` for `unique`, and one named single-column `index(...).on(table.field)` only for `index && !unique` ([rendering](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/cli/src/generators/drizzle.ts#L190-L225), [constraint emission](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/cli/src/generators/drizzle.ts#L275-L288)). Prisma similarly turns every indexed field into a one-field `@@index` and every unique field into a one-field unique block ([Prisma unique](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/cli/src/generators/prisma.ts#L280-L292), [Prisma indexes](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/cli/src/generators/prisma.ts#L459-L491)).

Consequently the definition language cannot express composite, partial/predicate, expression, included-column, ordered, operator-class, or method-specific indexes, nor explicit index/constraint names. Dialect-aware details live in generators—for example, the Prisma MySQL generator adds a length to string indexes—rather than in the declaration ([MySQL index projection](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/cli/src/generators/prisma.ts#L474-L490)). Hosts must add richer indexes in ORM/SQL schema outside Better Auth's model.

### Relations

A relation is a field-level `references: { model, field, onDelete? }`; `onDelete` is limited to five portable actions and defaults to cascade ([reference contract](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/type.ts#L223-L247)). There is no table-level foreign key, composite key, `onUpdate`, deferrability, match type, relation payload, or explicit relation/constraint name in the declaration.

The Drizzle generator turns the same reference into both a column `.references(...)` and Drizzle query relations. It derives a forward `one`; reverse cardinality is `one` when the foreign-key field is unique and otherwise `many`. Multiple foreign keys between the same two tables receive generated matching `relationName` values and collision-safe relation keys ([relation discovery](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/cli/src/generators/drizzle.ts#L328-L424), [relation rendering](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/cli/src/generators/drizzle.ts#L426-L470)).

Physical foreign keys alone are insufficient for Better Auth's experimental joined reads. The host's Drizzle schema must also define the Drizzle relation objects and pass those relation exports in the adapter's schema object; older schemas can be regenerated or manually amended ([official joins guidance](https://www.better-auth.com/docs/adapters/drizzle#joins-experimental)). If the relevant relation/query model is absent, the adapter logs an error and falls back to regular queries rather than failing authentication ([join fallback](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/drizzle-adapter/src/drizzle-adapter.ts#L693-L727), [fallback branch](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/drizzle-adapter/src/drizzle-adapter.ts#L730-L749)).

## 5. Type inference

The schema object is also a compile-time source. `DBFieldAttribute.type` maps to TypeScript primitives; `returned: false` removes output fields; `required: false` introduces optional/nullish output unless a literal default makes the output key present; `input: false`, optionality, and defaults determine input keys ([value/output/input inference](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/type.ts#L16-L92)). User/session/account model types intersect core Zod-inferred shapes with host additional fields and recursively inferred plugin fields ([user model composition](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/schema/user.ts#L9-L31), [plugin/option recursion](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/type.ts#L94-L162)).

Inference remains tied to the literal auth/plugin configuration, not to the generated ORM declarations. Renaming a database column therefore does not rename the Better Auth API property ([official logical-name guarantee](https://www.better-auth.com/docs/concepts/database#custom-tables)). Client inference also needs an explicit bridge: in one project, `inferAdditionalFields<typeof auth>()` imports the server instance type; across repositories, the fields must be repeated manually ([official client inference guidance](https://www.better-auth.com/docs/concepts/typescript#inferring-additional-fields-on-client)).

Two limits follow from the implementation:

- Runtime composition uses object replacement while type composition uses intersections. Duplicate plugin/host field keys with incompatible types can therefore become an unusable intersection at compile time while one declaration silently wins at runtime ([recursive intersection](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/type.ts#L120-L162), [runtime spreads](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/better-auth/src/db/schema.ts#L33-L55)).
- Runtime validators and transforms do not refine the inferred TypeScript type; inference sees only the coarse `DBFieldAttribute.type` mapping ([type mapping](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/type.ts#L16-L32), [validator/transform attributes](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/type.ts#L213-L260)).

## 6. Adapter metadata

`createAdapterFactory` passes every adapter the effective logical schema plus name-resolution helpers, field attributes, and input/output/where transformers. The helpers deliberately distinguish canonical schema keys, configured physical model names, and configured field names ([custom-adapter inputs](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/adapter/types.ts#L34-L129), [resolver construction](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/adapter/factory.ts#L90-L197)).

Adapter metadata is operational rather than full DDL capability metadata. The standard flags cover plural naming, numeric IDs, native UUID generation, JSON, dates, booleans, arrays, transactions, ID-generation behavior, key maps, and custom value transforms ([adapter config](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/adapter/index.ts#L52-L188)). The factory fills defaults and uses flags to translate JSON/arrays to strings, dates to ISO strings, and booleans to integers where needed ([factory defaults and transforms](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/adapter/factory.ts#L68-L88), [input conversion](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/adapter/factory.ts#L249-L288)).

The initialized adapter exposes its `adapterId`, standardized config, and adapter-specific options. The CLI consumes these values—for example Drizzle's provider, `camelCase`, and `usePlural`—to choose and parameterize a generator ([metadata exposure](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/core/src/db/adapter/factory.ts#L1659-L1678), [Drizzle metadata](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/drizzle-adapter/src/drizzle-adapter.ts#L1115-L1163), [generator use](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/cli/src/generators/drizzle.ts#L19-L45)). These flags do not describe SQL features such as generated columns, check constraints, composite indexes, upsert forms, returning support, or DDL alteration support.

## 7. Useful patterns for Commissary to carry into later decisions

These are observed patterns and requirements to consider, not a proposed Commissary definition API.

1. **One canonical logical schema can serve multiple consumers.** Better Auth reuses one composed schema for runtime mapping, API filtering, TypeScript inference, migration planning, and ORM generation. This avoids making an ORM declaration the authority for authentication semantics.
2. **Keep logical identity separate from physical names.** Stable schema keys plus table/field aliases let existing database names change without changing API property names. Relation targets remain canonical keys and resolve aliases late.
3. **Make contribution ownership and composition explicit.** Plugins can extend core tables and add new tables, but Better Auth's unchecked object spreads demonstrate why collision policy, precedence, and diagnostics matter.
4. **Separate portable semantics from adapter operations.** Capability flags and adapter transforms are useful for runtime value representation; generator-specific projection contains dialect/ORM details. The boundary makes the portable subset visible.
5. **Treat generation and adaptation as different contracts.** Drizzle replaces a generated artifact, Prisma structurally augments one, and Kysely introspects a live database. “Generate schema” alone does not specify preservation, reconciliation, or drift behavior.
6. **Treat ORM query relations separately from SQL foreign keys.** Better Auth must generate/pass both for joined reads. A foreign key can be valid while an ORM relation graph is missing.
7. **Keep externally managed objects present but migration-disabled.** `disableMigration` permits runtime use without claiming DDL ownership.

## 8. Limits that later Commissary tickets must not inherit accidentally

- The declaration vocabulary is deliberately lossy: only coarse field types, field-level uniqueness/indexes, and single-column references are portable.
- Composition has no ownership metadata, conflict error, or consistent same-key precedence across DDL metadata, runtime parsing, and TypeScript intersections.
- Drizzle source generation is whole-file replacement, not structural adaptation; only the Prisma path currently preserves and augments an existing ORM file.
- The Kysely migration diff is additive. It does not reconcile changed nullability/defaults/references/indexes on existing columns, rename objects, remove obsolete objects, or repair type mismatches.
- Existing Drizzle schemas supply runtime table objects and names, not inferred Better Auth definitions. Hosts still repeat/align the logical auth schema.
- Field `defaultValue`, `onUpdate`, transforms, and validators cross application and DDL concerns unevenly. The Drizzle and Prisma generators intentionally omit arbitrary default/update functions because application code cannot safely be embedded as ORM DDL ([Drizzle omission](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/cli/src/generators/drizzle.ts#L227-L273), [Prisma omission](https://github.com/better-auth/better-auth/blob/222facff556e6c570bbd6b7fd5923757b5a55711/packages/cli/src/generators/prisma.ts#L294-L377)).
- Adapter metadata is sufficient for Better Auth's narrow conversions and generators, not a general SQL capability model.
- Client type inference is not schema transport: it requires access to the server type or a repeated manual field declaration.

The main transferable lesson is the separation of canonical logical identity, composition, physical mapping, generation, and runtime adaptation. The main warning is that a compact schema DSL becomes ambiguous as soon as it is asked to represent richer indexes, relations, dialect behavior, or bidirectional reconciliation with an existing ORM schema.
