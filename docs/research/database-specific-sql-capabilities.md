# Database-specific SQL capabilities

Research snapshot: 2026-08-03. Sources are PostgreSQL 18, MySQL 8.4, current SQLite documentation, node-postgres `pg` 8.22.0 / `pg-cursor` 2.21.0 / `pg-copy-streams` 7.0.0, mysql2 3.23.2 at commit `5ebe8903d6aea2d8ea1490e11b52491526e50f19`, and better-sqlite3 13.0.2. This note identifies evidence for later interface decisions; it does **not** decide which Commissary Store interfaces survive.

## Executive answer

One portable “run SQL” capability can carry dialect-specific SQL text or a dialect query object, but it cannot by itself express every useful caller contract. The clearest counterexamples require a protocol state, unsolicited events, a pinned physical connection, callbacks into the host, or transfer of non-row data:

- PostgreSQL asynchronous `LISTEN`/`NOTIFY`, `COPY` byte streams, and portal/cursor lifecycle;
- MySQL client-provided `LOAD DATA LOCAL INFILE` streams and ordered heterogeneous multi-results from stored procedures or enabled multi-statements;
- SQLite online backup, database-image serialization, connection hooks/authorizer/progress control, and the optional session/changeset extension.

Cancellation and advisory locking also expose real semantics, but the three engines disagree about their target, lifetime, rollback effects, and required connection. A single portable contract could honestly promise only a deliberately weak common denominator. Prepared execution, ordinary row streaming, transaction/savepoint control, dialect grammar, result/schema metadata, and ergonomic `query`/`execute` spellings do not by themselves prove a database-specific Store specialization tier.

## Capability test

For this research, an operation earns consideration as a caller capability only when all of the following are true:

1. **The caller asks for a distinct effect or guarantee**, not merely a different spelling of SQL.
2. **The guarantee survives abstraction.** The adapter can preserve the required physical-session, transaction, stream, callback, ordering, cancellation, or cleanup lifecycle.
3. **Deletion removes an observable workflow.** If callers can replace the method with the lower-tier SQL operation without losing semantics, type information, resource safety, or bounded-memory behavior, the method is a thin alias.
4. **The implementation surface exists.** An engine feature not exposed by the selected driver is evidence about the database, not proof that a concrete TypeScript adapter can implement it without an additional driver escape hatch.

This test separates “PostgreSQL supports `NOTIFY`” from “the caller can subscribe to unsolicited notifications on a leased session”, and “MySQL has `GET_LOCK()`” from “the caller receives an exception-safe, session-pinned lock scope”.

## Comparison

| Asynchronous database messages | A session registers with `LISTEN`; notifications arrive asynchronously with channel, sender PID, and payload. Delivery is transaction-aware and duplicate notifications within one transaction may be folded ([PostgreSQL `NOTIFY`](https://www.postgresql.org/docs/18/sql-notify.html), [libpq notifications](https://www.postgresql.org/docs/18/libpq-notify.html)). node-postgres emits a `notification` event on `Client` ([client API](https://node-postgres.com/apis/client#notification)). | No equivalent SQL-session notification contract is documented in the inspected MySQL interface. | Connection hooks are callbacks about work on that connection, not a cross-session message channel; the update hook also has documented omissions ([SQLite update hook](https://www.sqlite.org/c3ref/update_hook.html)). | An ordinary query result cannot deliver unsolicited events while idle, retain a subscription on a pool lease, or define reconnect/unsubscribe behavior. A method that only executes `LISTEN` is nevertheless just a thin alias. |
| Bulk byte transfer | `COPY FROM STDIN`/`TO STDOUT` enters a distinct connection state, incrementally sends/receives bytes, and excludes other SQL on that connection until completion ([libpq COPY](https://www.postgresql.org/docs/18/libpq-copy.html)). `pg-copy-streams` exposes Node readable/writable streams and documents abort/chunk-boundary behavior ([first-party package README](https://github.com/brianc/node-pg-copy-streams/tree/v7.0.0)). | `LOAD DATA LOCAL INFILE` asks the client to supply local data; it must be enabled on both client and server and has explicit trust/security constraints ([MySQL security documentation](https://dev.mysql.com/doc/refman/8.4/en/load-data-local-security.html)). mysql2 accepts an `infileStreamFactory` and requires it rather than reading an arbitrary requested path ([mysql2 first-party interface](https://github.com/sidorares/node-mysql2/blob/master/website/docs/documentation/extras.mdx#sending-tabular-data-with-load-infile-and-local-stream)). | The inspected SQLite APIs have no corresponding client/server bulk-transfer state; prepared statement stepping is local row execution. | SQL text describes the command but cannot carry a backpressured source/sink, bound memory, abort protocol, connection exclusion, or the MySQL file-request trust boundary. PostgreSQL COPY and MySQL local infile are not the same wire contract. |
| Successive bounded fetch from one execution | A PostgreSQL cursor is backed by a portal and retrieves a bounded number of rows at a time; ordinary cursors are transaction-bound and `WITH HOLD` changes lifetime/materialization ([PostgreSQL `DECLARE`](https://www.postgresql.org/docs/18/sql-declare.html)). `pg-cursor` binds, executes, suspends, and closes a named portal ([first-party source](https://github.com/brianc/node-postgres/blob/master/packages/pg-cursor/index.js)). | The binary prepared-statement protocol can request a read-only server cursor and prefetch size ([MySQL `mysql_stmt_attr_set`](https://dev.mysql.com/doc/c-api/8.4/en/mysql-stmt-attr-set.html)); stored-program cursors are read-only, nonscrollable, and asensitive ([MySQL cursors](https://dev.mysql.com/doc/refman/8.4/en/cursors.html)). Current mysql2 does **not** expose that server-fetch capability: its `COM_STMT_EXECUTE` packet hard-codes `NO_CURSOR`; `query(...).stream()` instead applies Node backpressure by pausing/resuming the connection ([pinned execute source](https://github.com/sidorares/node-mysql2/blob/5ebe8903d6aea2d8ea1490e11b52491526e50f19/lib/packets/execute.js#L105-L118), [pinned stream source](https://github.com/sidorares/node-mysql2/blob/5ebe8903d6aea2d8ea1490e11b52491526e50f19/lib/commands/query.js#L273-L305)). | `sqlite3_step()` advances one prepared VM and returns one row at a time; the statement must eventually be reset or finalized ([SQLite prepare](https://www.sqlite.org/c3ref/prepare.html), [step](https://www.sqlite.org/c3ref/step.html)). better-sqlite3 exposes `Statement#iterate()` ([API](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md#iteratebindparameters---iterator)). | A portable row `Stream` can express bounded consumption, but it cannot promise a PostgreSQL portal, MySQL server cursor, SQLite VM, scrollability, holdability, or snapshot/lifetime details. Reissuing `LIMIT/OFFSET` is not equivalent to one execution. Dialect-specific cursor names alone are syntax, not a capability. |
| Multiple ordered results | PostgreSQL can return several results for a multi-command simple-query string, but this is not the same contract as MySQL stored-procedure results; node-postgres normally queues one active query. | `CALL` may produce an unknown number of result sets followed by a final status result; every result must be consumed, and failure to do so may drop the connection ([MySQL C API multiple-results contract](https://dev.mysql.com/doc/c-api/8.4/en/c-api-multiple-queries.html)). mysql2 models a heterogeneous union including nested row sets, header arrays, and a procedure packet ([first-party `QueryResult`](https://github.com/sidorares/node-mysql2/blob/master/typings/mysql/lib/protocol/packets/index.d.ts)). This is distinct from enabling semicolon-separated `multipleStatements`, which mysql2 disables by default and flags as an injection risk ([pinned connection type](https://github.com/sidorares/node-mysql2/blob/5ebe8903d6aea2d8ea1490e11b52491526e50f19/typings/mysql/lib/Connection.d.ts#L262-L269)). | One prepared SQLite statement compiles only the first statement in its SQL input; callers use the tail to prepare another statement ([SQLite prepare](https://www.sqlite.org/c3ref/prepare.html)). | A result type fixed to one row set or one command summary cannot represent unknown ordered row-set/status sequences. A `call()` method that only emits `CALL ...` is a thin alias; the possible capability is the result algebra and mandatory drain lifecycle. |
| Advisory/application lock scope | Session locks survive rollback until matching unlock/session end; transaction locks auto-release at transaction end and have no explicit unlock ([PostgreSQL advisory locks](https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS)). | `GET_LOCK()` is exclusive, named, reentrant/counting, server-wide, timeout-aware, released explicitly or at session end, and **not** released by commit/rollback; deadlock ends the acquisition request but does not roll back a transaction ([MySQL locking functions](https://dev.mysql.com/doc/refman/8.4/en/locking-functions.html)). | No corresponding server-wide named advisory lock exists; SQLite’s file/transaction locking is database concurrency control, not an application-defined lock namespace ([SQLite transactions](https://www.sqlite.org/lang_transaction.html)). | Raw SQL can invoke each function, but a pool-agnostic call cannot guarantee physical-session affinity or exception-safe release. PostgreSQL transaction locks cannot be honestly promised by a MySQL implementation, and SQLite has no equivalent. The semantic candidate is a bracketed pinned scope, not a dialect-named SQL wrapper. |
| Cancel active work | A separate PostgreSQL cancel request targets the backend’s current command; successful dispatch explicitly does not guarantee effect ([libpq cancellation](https://www.postgresql.org/docs/18/libpq-cancel.html)). | `KILL QUERY id` sets a flag checked at operation-specific intervals, returns without waiting for confirmation, requires another executing connection, and can leave nontransactional modifications unrolled back ([MySQL `KILL`](https://dev.mysql.com/doc/refman/8.4/en/kill.html)). mysql2 exposes the target `threadId`, but its query timeout only reports a local `PROTOCOL_SEQUENCE_TIMEOUT`; it does not send `KILL` ([pinned timeout source](https://github.com/sidorares/node-mysql2/blob/5ebe8903d6aea2d8ea1490e11b52491526e50f19/lib/commands/query.js#L338-L359)). | `sqlite3_interrupt(db)` is safe from another thread, applies to currently running statements on one connection, and an interrupted write in an explicit transaction rolls back that entire transaction ([SQLite interrupt](https://www.sqlite.org/c3ref/interrupt.html)). | A portable cancellation request can honestly be best-effort, but not “the statement stopped”, per-query targeting, session preservation, or uniform rollback. Dropping a Promise or enforcing only a client timeout is not server/engine cancellation. |
| Live backup | Server backup/replication facilities exist outside the inspected PostgreSQL SQL-client Store surface. | Server backup facilities exist outside the inspected MySQL SQL-client Store surface. | The online backup API incrementally copies one database to another. The destination stays in a write transaction while source locks are step-local, allowing a live source; retry and restart behavior is explicit ([SQLite online backup](https://www.sqlite.org/c3ref/backup_finish.html)). better-sqlite3 exposes `Database#backup()` with progress and cancellation ([API](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md#backupdestination-options---promise)). | Executing `VACUUM INTO` or copying a file does not preserve incremental progress, live-source lock behavior, retryability, restart rules, or cancellation. This is an embedded-database operation, not portable SQL query execution. |
| Database image import/export | No comparable database-as-bytes connection API in the inspected client surface. | No comparable database-as-bytes connection API in the inspected client surface. | `sqlite3_serialize()` returns the exact database-file byte image (or the bytes an in-memory/TEMP database would write); no-copy mode has connection/write lifetime restrictions and the API can be compile-time omitted ([SQLite serialization](https://www.sqlite.org/c3ref/serialize.html)). better-sqlite3 exposes `Database#serialize() -> Buffer`, and accepts that buffer when opening an in-memory database ([API](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md#serializeoptions---buffer)). | Rows are not a database image. Serialization also must not be mislabeled as online backup: it is a memory image, not an incremental lock-aware copy protocol. |
| Host callbacks and execution policy | Server-side triggers/functions are database objects; the inspected node-postgres Store-facing client does not install host callbacks into statement compilation/execution. | Server-side routines/plugins are not the same as connection-local host callbacks in the inspected mysql2 interface. | SQLite installs one connection-local callback per hook kind. Commit hooks can veto commit; authorizers allow/deny/replace reads during compilation; progress handlers can interrupt long prepare/step work; update hooks report limited rowid-table changes ([commit/rollback hooks](https://www.sqlite.org/c3ref/commit_hook.html), [authorizer](https://www.sqlite.org/c3ref/set_authorizer.html), [progress handler](https://www.sqlite.org/c3ref/progress_handler.html), [update hook](https://www.sqlite.org/c3ref/update_hook.html)). | SQL cannot carry host callbacks or their reentrancy, replacement, timing, and veto rules. A vague portable `onChange` would overclaim: SQLite update hooks omit `WITHOUT ROWID`, some REPLACE/truncate deletions, and do not specify before/after timing. |
| Change capture/apply | Logical decoding is a server replication facility with a different protocol and operational model; it is not evidenced here as an ordinary node-postgres Store interface. | Binary log consumption is a replication facility, not evidenced here as a stable mysql2 Store query contract. | The optional session extension records configured tables, emits changeset/patchset blobs, applies with caller-directed conflict handling, and can invert a changeset for undo. It requires compile flags and declared non-null primary keys and does not capture virtual tables ([SQLite session extension](https://www.sqlite.org/sessionintro.html)). | Polling rows or update hooks do not provide a portable, replayable changeset with original values, coalescing, inversion, and conflict application. Build-option and driver exposure must be checked before promising it. |
| Runtime SQL environment extension | Extension installation is normally server administration. | Plugins/functions are normally server administration. | Loadable extensions can add functions, collations, virtual tables, and VFSes; loading is disabled by default for security ([SQLite loadable extensions](https://www.sqlite.org/loadext.html)). better-sqlite3 exposes connection-local `loadExtension`, `function`, `aggregate`, and `table` operations ([API](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md)). | These operations alter what SQL means on one embedded connection and invoke host code. They are real capabilities, but evidence places them at configured-connection/construction scope; their existence does not by itself prove an integration Store should own them. |

## Guarantees that force a session or resource scope

The physical connection is part of several contracts. node-postgres explicitly states that all statements in a transaction must use the same `Client` and that `pool.query` must not be used for a transaction ([transaction guide](https://node-postgres.com/features/transactions)). The same fact follows for PostgreSQL subscriptions, session advisory locks, named prepared statements, and held portals. MySQL named locks and `LOAD DATA LOCAL` similarly attach behavior to one protocol session. SQLite hooks, interrupt, prepared statements, backup handles, and loaded extensions attach to one `sqlite3*`.

Therefore, a portable SQL method that borrows a pool connection for each call cannot implement these guarantees merely by generating the right SQL. The deletion test should be applied to the **scope** as well as the operation: after deleting a lease/bracket, can the implementation still prove that acquisition, use, cleanup, and asynchronous events occur on the same live physical connection? If not, the scope is substantive. This observation does not decide whether the scope belongs in a portable tier, a database-specific tier, a driver escape hatch, or nowhere in Commissary.

## Candidates that do not independently prove a database-specific Store tier

### Dialect syntax

`RETURNING`, conflict/upsert forms, lock clauses, JSON operators, `PRAGMA`, `VACUUM INTO`, `LISTEN`, `NOTIFY`, `COPY`, `LOAD DATA`, `CALL`, `KILL`, `GET_LOCK`, and PostgreSQL advisory-lock functions are SQL grammar or functions. The spelling belongs in a dialect query representation. A separate method is justified only when it carries semantics that SQL text cannot: an event stream, byte stream, multi-result drain, pinned scope, callback, progress handle, or cleanup guarantee.

A particularly useful negative example is PostgreSQL `notify(channel, payload)`: `pg_notify(text,text)` already permits dynamic values ([PostgreSQL `NOTIFY`](https://www.postgresql.org/docs/18/sql-notify.html)). A wrapper that only calls it does not add a capability. The receiving subscription is different because delivery is unsolicited and session-local.

### `query` versus `execute`

Database libraries often use these names for protocol/result-shaping choices rather than two semantic database effects. node-postgres accepts SQL text, parameters, or a query configuration through one `client.query` ([client API](https://node-postgres.com/apis/client#clientquery)). mysql2’s SELECT examples explicitly say they also work with `execute`; `query` uses the text protocol while prepared `execute` uses the prepared/binary protocol ([mysql2 query interface](https://sidorares.github.io/node-mysql2/docs/examples/queries/simple-queries/select), [MySQL prepared interface](https://dev.mysql.com/doc/c-api/8.4/en/c-api-prepared-statement-interface.html)). better-sqlite3 prepares a statement and then offers `run/get/all/iterate` result collectors ([API](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md)).

The deletion question is semantic: if deleting one name still permits the same statement, bindings, rows/command result, errors, and lifecycle through the other, the removed name was a thin alias. For mysql2, deletion is **not** behavior-preserving when a caller specifically requires server preparation/cache reuse or binary parameter/result transport: `query` formats and sends text while `execute` prepares and sends a statement execution ([pinned connection source](https://github.com/sidorares/node-mysql2/blob/5ebe8903d6aea2d8ea1490e11b52491526e50f19/lib/base/connection.js#L637-L653), [pinned execute source](https://github.com/sidorares/node-mysql2/blob/5ebe8903d6aea2d8ea1490e11b52491526e50f19/lib/commands/execute.js#L41-L64)). Protocol optimization or whether rows are collected is evidence for an option or prepared-execution guarantee, not automatically for a wider Store specialization tier.

### Prepared statements

All three engines have reusable prepared execution. PostgreSQL named prepared statements are connection-local and node-postgres parses once per client when a query has a `name` ([query guide](https://node-postgres.com/features/queries#prepared-statements)). MySQL’s prepared interface parses once, re-executes through a binary protocol, and may automatically reprepare after metadata changes ([C API guide](https://dev.mysql.com/doc/c-api/8.4/en/c-api-prepared-statement-interface.html)). SQLite compiles the first statement to bytecode, binds/steps it, and requires finalize/reset lifecycle ([prepare](https://www.sqlite.org/c3ref/prepare.html)).

Those implementation guarantees differ, but safe parameter binding and reusable execution can be expressed as a portable lowest-common-denominator capability. A database-specific `prepare` earns a seam only if a caller requires a stronger observable guarantee such as PostgreSQL name collision/lifetime, MySQL binary-protocol behavior, or SQLite statement-tail/reprepare behavior. Merely spelling parameter markers differently is dialect syntax.

### Transactions, savepoints, and isolation

Atomic transactions and nested savepoint behavior are real caller capabilities, but they exist across all three databases. Engine-specific isolation levels, PostgreSQL aborted-transaction state, MySQL storage-engine/autocommit details, and SQLite `DEFERRED`/`IMMEDIATE`/`EXCLUSIVE` plus single-writer behavior constrain what an implementation may promise; they do not automatically require one interface per database. For SQLite specifically, `BEGIN` does not nest and nested work uses savepoints ([SQLite transactions](https://www.sqlite.org/lang_transaction.html)); better-sqlite3’s transaction helper simply maps nested calls to savepoints and exposes mode variants ([API](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md#transactionfunction---function)).

### Row delivery, metadata, and schema inspection

Buffered rows, array/object row shapes, field metadata, affected-row counts, insert IDs, command tags, and column type information are result representation or metadata. `INFORMATION_SCHEMA`, PostgreSQL catalogs, and SQLite `PRAGMA` are schema metadata. They may require honest dialect-specific types, but they are not distinct effects merely because their fields differ.

Likewise, a portable `Stream<Row>` can state bounded row consumption and scoped cleanup without promising that every backend uses the same cursor mechanism. A database-specific portal/cursor interface is justified only if callers need its stronger lifecycle, snapshot, fetch-count, holdability, or server-resource guarantees.

## Interface deletion tests for later tickets

Apply these tests to a proposed interface without assuming the answer:

1. **Notification subscription:** after deletion, can a caller still receive unsolicited channel/payload/sender events while idle, and can it delimit subscription lifetime on one session? Polling is not equivalent. If only a `LISTEN` helper disappears and the event stream remains, the helper was an alias.
2. **Bulk transfer:** after deletion, can a caller still send/receive incrementally with backpressure, bounded memory, abort completion, and exclusive connection state? Passing a buffered array or file path is not equivalent.
3. **Cursor/row stream:** after deletion, can a caller still fetch bounded successive rows from the same execution and close it safely? Reissuing pagination is not equivalent. If only a dialect cursor name disappears while the same scoped stream remains, no capability was lost.
4. **MySQL multi-results:** after deletion, can a caller still observe every ordered row-set/status result and guarantee the protocol is fully drained? Returning only the first rows is not equivalent. A `CALL` spelling helper is replaceable.
5. **Advisory lock:** after deletion, can a caller still obtain the promised wait/try behavior on one physical session and guarantee release on success, failure, interruption, transaction end, or session end as applicable? Raw SQL without bracketing does not preserve cleanup; a raw SQL wrapper adds nothing.
6. **Cancellation:** after deletion, can a caller still target active engine work rather than merely stop awaiting it? Any retained contract must state best-effort dispatch, target scope, connection survival, and transaction effects; otherwise the three engines are being falsely normalized.
7. **SQLite backup/serialization:** after deletion, can a caller still obtain the same incremental live backup or exact database image without a driver escape hatch? Do not accept `VACUUM INTO`, filesystem copy, and serialization as interchangeable.
8. **SQLite hooks/policy:** after deletion, can a caller still veto commit, authorize statement compilation, receive the documented limited update callback, or cooperatively interrupt progress? A single generic `onChange` does not preserve these distinct contracts.
9. **SQLite changesets:** after deletion, can a caller still capture, coalesce, invert, transmit, conflict-resolve, and apply compatible changes? Update notifications or polling fail this test.
10. **Prepared execution:** after deletion, can a caller still reuse one compiled/prepared statement with bindings and deterministic cleanup? If yes, a dialect-specific prepare method is likely an alias. If only parameterized one-shot execution is required, preparation is an optimization rather than a distinct integration need.
11. **`query`/`execute`:** delete each in turn. If every caller-observable input, output, error, and resource guarantee remains through the other, two names do not form two capability levels.
12. **Database-specific Store name:** delete the entire specialization tier. If all surviving members are dialect query types, metadata/result types, or aliases over the portable tier, no caller capability was deleted. If a stream, callback, resource scope, or engine guarantee becomes inaccessible except through the raw driver, the lost member has at least passed the first deletion test.

## Design implications, without choosing interfaces

- “Supports arbitrary dialect SQL” and “supports every database capability” are different claims. Protocol states, host callbacks, unsolicited events, and database images cannot be encoded in SQL text alone.
- The deepest recurring seam is usually a scoped resource/lifecycle, not a method named after a command. Any later specification must state pinning, interruption, cleanup, and pool-return behavior before claiming LISTEN, COPY, locks, cursors, local infile, or hooks.
- Lowest-common-denominator portability is plausible for parameterized execution, prepared execution, transactions/savepoints, row streams, and best-effort cancellation intent. Stronger engine guarantees must not leak into that common contract accidentally.
- Some real database capabilities belong to host configuration or operations rather than integration-facing Store use. SQLite extension loading/UDF registration and backup are genuine capabilities, but their existence alone does not assign ownership to a Commissary Store.
- Availability must be checked against the selected driver and build. SQLite sessions/serialization can be compile-option dependent; PostgreSQL pipeline/COPY/cursor behavior may require a companion package; MySQL LOCAL loading must be enabled and guarded. An engine feature without a supported adapter path should not become a promised no-op.
