# Rich Tool results across agent frameworks

Research snapshot: Vercel AI SDK `7.0.41` (`2ab3f34`), Effect AI (`9867b9f`), OpenCode (`a45c2b917`), TanStack AI (`1120f0f`), pi-mono (`027a5847`), Hermes Agent (`097f0d016`), and MCP specification `2025-06-18`. Local paths below are read-only reference repositories under `.repos/`; MCP citations are official specification URLs.

## Source-backed notes

### Vercel AI SDK

The durable distinction is `OUTPUT` versus `ToolResultOutput`. `execute` owns arbitrary typed business output, while `toModelOutput` receives that value together with call id and input and returns the provider-facing tagged union [`.repos/vercel-ai/packages/provider-utils/src/types/tool.ts:12-43`, `.repos/vercel-ai/packages/provider-utils/src/types/tool.ts:113-145`]. The model union supports direct text, JSON, errors/denial, or a content list; current rich media is represented as `file` with media type and tagged data, including bytes, URL, provider reference, or inline text [`.repos/vercel-ai/packages/provider-utils/src/types/content-part.ts:247-383`].

An `outputSchema` is therefore primarily a type/schema declaration, not automatic post-execution validation: the execution path constructs `TypedToolResult` directly from `part.output`/handler output [`.repos/vercel-ai/packages/ai/src/generate-text/execute-tool-call.ts:146-206`]. The explicit validation located in core is for replayed/UI messages, and it validates `toolPart.output` only when state is `output-available` and the tool has a schema [`.repos/vercel-ai/packages/ai/src/ui/validate-ui-messages.ts:519-526`]. With no schema, executable tools still infer their output from `execute`; model projection still defaults to JSON [`.repos/vercel-ai/packages/provider-utils/src/types/tool.ts:16-31`, `.repos/vercel-ai/packages/provider-utils/src/types/tool.ts:113-121`].

### Effect AI

Effect makes success and failure schemas intrinsic to a Tool. User-defined tools default success to `Schema.Void` (or `Schema.Unknown` for the schema-less constructor), failure to `Schema.Never`, and parameters to an empty/unknown schema [`.repos/effect/packages/effect/src/unstable/ai/Tool.ts:1263-1273`, `.repos/effect/packages/effect/src/unstable/ai/Tool.ts:1360-1374`]. Toolkit execution compiles parameter decoding plus result decoding/encoding; handler results are encoded through the success/failure union, and schema failures become typed AI errors [`.repos/effect/packages/effect/src/unstable/ai/Toolkit.ts:249-267`, `.repos/effect/packages/effect/src/unstable/ai/Toolkit.ts:289-353`]. This validates business output.

The model-facing Prompt representation is still a generic `result: unknown` with `isFailure`, not a rich text/image/file union [`.repos/effect/packages/effect/src/unstable/ai/Prompt.ts:635-710`]. The Response layer retains both decoded `result` and schema-derived `encodedResult` [`.repos/effect/packages/effect/src/unstable/ai/Response.ts:1472-1550`]. There is no separate content projection or second schema for what the model sees.

### OpenCode

OpenCode standardizes a useful application/UI envelope: title, arbitrary metadata, string output, and optional file attachments [`.repos/opencode/packages/opencode/src/tool/tool.ts:45-61`]. Its wrapper compiles and applies only the parameter decoder, runs the handler, truncates the output string, and carries metadata forward [`.repos/opencode/packages/opencode/src/tool/tool.ts:107-151`]. Consequently there is no output-schema behavior to apply when absent—it is always absent.

At model conversion, attachments supported as tool-result media remain beside the text; images/PDFs unsupported by a provider are extracted for a separate user message [`.repos/opencode/packages/opencode/src/session/message-v2.ts:295-313`]. MCP mapping collects text, converts images to data-URL attachments, and converts embedded resources to either text or binary attachments [`.repos/opencode/packages/opencode/src/session/tools.ts:426-475`, `.repos/opencode/packages/opencode/src/session/tools.ts:535-574`]. This is a fixed projection, not user-defined conversion, and it does not preserve a separately queryable structured business value.

### OpenCode LLM package

OpenCode also contains a lower-level LLM package with a deeper contract than its application Tool API. Typed Tools declare parameter and success schemas. The runtime decodes input, executes the handler, encodes the success value through its schema, and only then projects it [`.repos/opencode/packages/llm/src/tool-runtime.ts:37-58`].

Its projected `ToolOutput` has two sibling fields: `structured` and ordered `content` [`.repos/opencode/packages/llm/src/schema/messages.ts:80-109`]. `toStructuredOutput` can change the structured model value, while `toModelOutput` creates text/file content from the validated output [`.repos/opencode/packages/llm/src/tool.ts:238-249`]. Dynamic Tools can omit `outputSchema`; their runtime encoder is the identity function [`.repos/opencode/packages/llm/src/tool.ts:165-184`]. This is the closest surveyed example of schema-validated business output followed by a separate rich-content projection.

### TanStack AI

TanStack supports optional input/output Standard Schema or plain JSON Schema on server/client tool definitions [`.repos/tanstack-ai/packages/ai/src/activities/chat/tools/tool-definition.ts:71-133`]. Output inference is precise for Standard Schema, `unknown` for plain JSON Schema, and `unknown` when absent [`.repos/tanstack-ai/packages/ai/src/activities/chat/tools/tool-definition.ts:176-191`]. On execution, Standard Schema output is parsed even when nullish, so the schema—not a truthiness check—decides validity; the validated/transformed value remains business output [`.repos/tanstack-ai/packages/ai/src/activities/chat/tools/tool-calls.ts:361-381`].

The next step is fixed normalization: string unchanged, a narrowly detected non-empty all-valid `ContentPart[]` unchanged, otherwise JSON serialization [`.repos/tanstack-ai/packages/ai/src/utilities/tool-result.ts:27-65`]. Thus no-schema behavior is permissive and still rich if the handler returns the recognized content array. MCP App `ui://` resources demonstrate a second deliberate channel: they emit UI events and “never enter model input” [`.repos/tanstack-ai/packages/ai/src/activities/chat/tools/tool-calls.ts:50-70`].

### pi-mono

pi-mono makes the split part of the handler return rather than deriving it: `content` is the text/image material returned to the model, while generic `details` is arbitrary structured data for logs/UI [`.repos/pi-mono/packages/agent/src/types.ts:354-359`]. `AgentTool.execute` returns that envelope and has parameters typed by TypeBox, but defines no output schema or conversion callback [`.repos/pi-mono/packages/agent/src/types.ts:379-394`]. Tool-result transcript messages carry the content directly, while application events also expose details [`.repos/pi-mono/packages/agent/src/harness/types.ts:626-634`]. No-schema behavior is therefore the only behavior: the contract is structurally typed but not schema-validated at runtime in this layer.

### Hermes Agent

Hermes treats tool output as model-ready serialization. The registry admits a string or one specially tagged multimodal dictionary and converts every other handler return into a JSON error string [`.repos/hermes-agent/tools/registry.py:570-611`]. A post-dispatch `transform_tool_result` lifecycle hook can rewrite only the final string and ignores non-string hook returns [`.repos/hermes-agent/model_tools.py:1384-1415`]. This validates transport shape only; there is no declared output/business schema.

Its MCP adapter flattens MCP’s two output channels: text plus `structuredContent` becomes one JSON string, while structured-only or text-only results become `{ "result": ... }` [`.repos/hermes-agent/tools/mcp_tool.py:4706-4712`]. That is simple and model-readable, but application code cannot independently consume the structured result without parsing the same serialized model payload.

### MCP Tool protocol

MCP natively carries two sibling representations. `structuredContent` is a JSON object for structured result data; `content` is an ordered rich-content list with text, image, audio, resource-link, and embedded-resource forms [official tools spec, “Tool Result”](https://modelcontextprotocol.io/specification/2025-06-18/server/tools#tool-result), [official tools spec, “Structured Content”](https://modelcontextprotocol.io/specification/2025-06-18/server/tools#structured-content). The specification explicitly says this is unrelated to schema-constrained model generation and recommends duplicating serialized structured JSON as text for backward compatibility [official tools spec, “Structured Content”](https://modelcontextprotocol.io/specification/2025-06-18/server/tools#structured-content).

`outputSchema` governs only `structuredContent`: conforming server output is mandatory and client validation is recommended [official tools spec, “Output Schema”](https://modelcontextprotocol.io/specification/2025-06-18/server/tools#output-schema). The independent content list has its own structural protocol types but is not the value tested against `outputSchema`. Without an output schema, servers may still return structured and/or rich content; no schema-conformance requirement applies [official tools spec, “Tool Result”](https://modelcontextprotocol.io/specification/2025-06-18/server/tools#tool-result).

## Viable Commissary contract patterns (recommendations, not findings)

These are design options inferred from the evidence above; no option is selected.

### 1. Business value plus explicit projection

```ts
type Tool<I, O> = {
  inputSchema: Schema<I>;
  outputSchema?: Schema<O>;
  execute(input: I): Promise<O>;
  toModelOutput?(ctx: { input: I; output: O; callId: string }): ModelContent;
};
```

Validate `O` when `outputSchema` exists; otherwise accept `unknown`. Default projection can be JSON. This matches Vercel’s deep separation and permits provider-neutral files/images, redaction, summarization, and UI-only fields. Trade-offs: two contracts must be documented; projection failures need their own error semantics; MCP import must decide whether `structuredContent` is `O` and `content` overrides the projection.

### 2. Dual-channel result envelope

```ts
type ToolResult<O = unknown> = {
  output?: O;
  content: ModelContent[];
  artifacts?: ArtifactRef[];
  isError?: boolean;
};
```

Validate only `output` against an optional output schema; validate `content` against a framework-owned content schema. This follows MCP and pi-mono, makes business/model separation visible at every callsite, and supports faithful MCP passthrough. Trade-offs: handlers must usually produce both views; consistency can drift; requiring content is verbose, while generating it by default partially recreates pattern 1.

### 3. Canonical result plus deterministic framework projection

```ts
type ToolResult<O = unknown> =
  { type: "data"; value: O } | { type: "content"; value: ModelContent[]; data?: O };
```

The framework validates `value`/`data` when a schema exists and deterministically projects data as JSON; recognized content passes through. This resembles TanStack’s low-ceremony normalization while avoiding accidental array-shape detection through an explicit discriminator. Trade-offs: simple and durable, but per-tool redaction or model-specific summaries require middleware; a single canonical projection may be too blunt for large structured results; MCP needs a mechanical mapping from `structuredContent` and `content` into the union.
