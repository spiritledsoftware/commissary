# Standard Schema SQL inference

Research snapshot: 2026-08-03. Commissary currently resolves `@standard-schema/spec` `1.1.0` ([lockfile](../../pnpm-lock.yaml#L276-L278)). This note answers the runtime-shape and SQL-inference questions; it deliberately does not choose Commissary's final public interface.

## Answer in brief

`StandardSchemaV1` alone is a validation protocol, not a reflection protocol. At runtime it guarantees a version, vendor name, and validation function; its input/output `types` member is optional type metadata used for TypeScript inference, not a required inspectable shape description ([Standard Schema V1 interface](https://github.com/standard-schema/standard-schema/blob/main/packages/spec/schema.md#the-interface), [design goals](https://github.com/standard-schema/standard-schema/blob/main/packages/spec/schema.md#design-goals)). Calling `validate` on examples cannot soundly discover a schema's accepted output set, so SQL inference from Standard Schema alone is impossible.

`StandardJSONSchemaV1` is the portable reflection seam. It separately exposes `jsonSchema.input(...)` and `jsonSchema.output(...)`, either converter may throw, and target support is best-effort ([Standard JSON Schema V1 interface](https://github.com/standard-schema/standard-schema/blob/main/packages/spec/json-schema.md#the-interface), [conversion error contract](https://github.com/standard-schema/standard-schema/blob/main/packages/spec/json-schema.md#what-about-error-handling)). Persisted shape must be classified from **output**, not input: the spec split exists specifically because validation may transform, for example, a string input into a number output ([input/output rationale](https://github.com/standard-schema/standard-schema/blob/main/packages/spec/json-schema.md#why-both-jsonschemainput-and-jsonschemaoutput)).

Even an output JSON Schema describes valid JSON instances, not database intent. It can unambiguously identify a small set of value families, but it cannot generally choose integer width, numeric precision/scale, text length/storage class, temporal representation, binary encoding, JSON-vs-normalized structure, default generation, keys, indexes, or uniqueness. Those cases need explicit storage mapping or a definition error rather than a guess.

## What exists at runtime

| Source | Required runtime information | Shape information usable for SQL |
| --- | --- | --- |
| `StandardSchemaV1` | `~standard.version === 1`, `vendor`, and `validate(unknown)`, producing either an output value or issues; validation may be synchronous or asynchronous ([interface](https://github.com/standard-schema/standard-schema/blob/main/packages/spec/schema.md#the-interface)). | None beyond values observed in individual successful calls. `types.input` and `types.output` power static inference but are optional and do not enumerate a runtime domain ([same interface](https://github.com/standard-schema/standard-schema/blob/main/packages/spec/schema.md#the-interface)). |
| `StandardJSONSchemaV1` | `version`, `vendor`, and separate input/output converters accepting a target. The interface is orthogonal to Standard Schema and contains no validator ([FAQ](https://github.com/standard-schema/standard-schema/blob/main/packages/spec/json-schema.md#whats-the-relationship-between-this-and-standard-schema)). | The returned JSON Schema object, if conversion succeeds. It may contain primitive type assertions, unions/applicators, references, constraints, and annotations. |
| JSON Schema Draft 2020-12 | Six primitive JSON types plus `integer`, where `integer` means a JSON number with zero fractional part ([validation §6.1.1](https://json-schema.org/draft/2020-12/json-schema-validation.html#name-type)). JSON numbers are not bounded by the specification ([validation §4.2](https://json-schema.org/draft/2020-12/json-schema-validation.html#name-validation-of-numeric-instan)). | A semantic instance set, not a physical representation. `format` is annotation-only by default ([validation §7.2.1](https://json-schema.org/draft/2020-12/json-schema-validation.html#name-format-annotation-vocabular)); `default` is also metadata, not a mandate to populate a value ([validation §9.2](https://json-schema.org/draft/2020-12/json-schema-validation.html#name-default)). |

Two distinctions matter:

1. **Output shape is not input shape.** Coercions, defaults, transforms, and morphs can change the value family. A store mapping that follows input JSON Schema can create a column that cannot hold the validated output; Standard JSON Schema provides `output` precisely to avoid that loss ([spec rationale](https://github.com/standard-schema/standard-schema/blob/main/packages/spec/json-schema.md#why-both-jsonschemainput-and-jsonschemaoutput)).
2. **Missing is not null.** JSON Schema's `required` only controls whether an object property name is present, while `null` is its own primitive instance type ([required §6.5.3](https://json-schema.org/draft/2020-12/json-schema-validation.html#name-required), [type §6.1.1](https://json-schema.org/draft/2020-12/json-schema-validation.html#name-type)). At a field-schema boundary there is no enclosing JSON Schema `required` list, so omission must come from the field-definition contract or explicit metadata; it cannot be inferred from a scalar root schema.

## Current Commissary Core fields

The Store's `FieldSchema<Input, Output>` is only `StandardSchemaV1`, with output statically restricted to JSON-compatible data or `undefined`; it does not require `StandardJSONSchemaV1` ([field contract](../../packages/store/src/record.ts#L6-L16)). A field may also have distinct select/create/update schemas, and omitted operation schemas fall back toward select ([operation schemas](../../packages/store/src/record.ts#L18-L28), [fallback rules](../../packages/store/src/record.ts#L168-L183)). The selected output is therefore the persistence-facing shape, while create/update outputs must remain round-trip compatible with it ([round-trip constraint](../../packages/store/src/record.ts#L63-L84)).

Core's schema factory emits only `version`, `vendor: "commissary"`, and `validate`; it attaches no JSON Schema converter or shape tag ([factory](../../packages/core/src/store-records.ts#L58-L74)). The instantiated objects are thus indistinguishable to a generic runtime classifier except by vendor and validation behavior. The private factories nevertheless establish these source-known contracts:

| Core validator | Actual accepted output | SQL inference consequence |
| --- | --- | --- |
| `requiredStringField` | Any nonempty JavaScript string ([implementation](../../packages/core/src/store-records.ts#L76-L84)). | Text-family shape is clear; length, collation, and identifier intent are not. Compile-time ID brands add no runtime distinction. |
| `optionalStringField` | `undefined` or any nonempty string ([implementation](../../packages/core/src/store-records.ts#L86-L100)). | Text-family shape plus omission is source-known, but generic runtime reflection cannot see either fact. `undefined` is omission, not SQL `NULL`. |
| `requiredNumberField` | Any finite JavaScript number, including fractional and safe/unsafe integer-valued doubles ([implementation](../../packages/core/src/store-records.ts#L102-L105)). | A numeric family is known, but integer vs floating vs exact decimal, width, and overflow policy are not. |
| `requiredBooleanField` | A JavaScript boolean ([implementation](../../packages/core/src/store-records.ts#L108-L110)). | Logical boolean shape is clear; physical dialect encoding remains adapter-specific. |
| `literalStringField` | One member of a supplied string set ([implementation](../../packages/core/src/store-records.ts#L112-L123)). | Text-family shape and an enum/check constraint are source-known; the runtime schema object does not expose the set. |
| `requiredJsonField` / `optionalJsonField` | Finite, acyclic JSON scalar/array/plain-object data, optionally `undefined` ([implementations](../../packages/core/src/store-records.ts#L125-L149), [JSON predicate](../../packages/store/src/json.ts#L15-L56)). | The factory's generic `Value` is not checked structurally at runtime. A value might be a scalar or document, so a single SQL type cannot be inferred from the schema object. |

The built-in definitions reuse these factories for IDs, names, statuses, counters, booleans, messages, results, and other JSON documents ([durable fields](../../packages/core/src/store-records.ts#L151-L198), [runtime-state examples](../../packages/core/src/store-records.ts#L209-L257)). Consequently, **all current Core fields need source-owned storage metadata/mapping before a generic SQL adapter can define columns**. Their private factory identity is not runtime evidence, and speculative validation probes would neither prove the full domain nor recover enum members or omission semantics.

## Representative compatible libraries

The Standard Schema project lists Zod 3.24+, Valibot 1.0+, ArkType 2.0+, and Effect Schema via adapter among compatible validators; Standard JSON Schema support is a separate, narrower list and currently includes Zod 4.2+, ArkType 2.1.28, and Valibot through `toStandardJsonSchema` ([Standard Schema implementers](https://github.com/standard-schema/standard-schema/blob/main/packages/spec/schema.md#what-schema-libraries-implement-the-spec), [Standard JSON Schema implementers](https://github.com/standard-schema/standard-schema/blob/main/packages/spec/json-schema.md#what-schema-libraries-support-this-spec)). Compatibility with validation therefore does not imply runtime shape conversion.

| Library | First-party evidence | Consequence for inference |
| --- | --- | --- |
| **Zod 4** | `z.toJSONSchema` normally emits the output shape and can emit the input shape with `io: "input"`; a string-to-number pipe demonstrates the difference ([Zod `io`](https://zod.dev/json-schema?id=io#io)). BigInt, Date, Map, Set, transforms, custom schemas, `undefined`, `NaN`, and other constructs are unrepresentable and throw by default; opting into `"any"` reduces them to `{}` ([Zod unrepresentable types](https://zod.dev/json-schema?id=unrepresentable#unrepresentable)). | Use the Standard JSON Schema **output** converter. A thrown conversion or permissive `{}` is an inference failure, not evidence for a catch-all column. |
| **Valibot** | Its official converter has `typeMode: "input" | "output"`; the documented decimal-string transform emits `string` for input and `number` for output ([Valibot conversion modes](https://valibot.dev/blog/json-schema-package-upgrade/#convert-input-or-output-of-schema)). Valibot documents that only a large part of its schemas convert and that JSON Schema cannot cover non-JSON structures or transformations generally ([JSON Schema guide](https://valibot.dev/guides/json-schema/#cons-of-json-schema)). Overrides can manually represent otherwise unsupported shapes, such as Date as a date-time string ([override example](https://valibot.dev/blog/json-schema-package-upgrade/#override-default-json-schema-conversion)). | Successful output conversion can be classified, but an override is an explicit user/library mapping whose declared representation must be trusted as such; it should not be silently invented by the store. |
| **ArkType** | ArkType co-authored and implements Standard Schema, and each Type has `toJsonSchema` with target/fallback/cycle options ([integrations](https://arktype.io/docs/integrations#standard-schema), [JSON Schema conversion](https://arktype.io/docs/integrations#type-to-json-schema)). Its conversion configuration exposes fallbacks for unsupported semantics, including morph/transformation behavior ([configuration](https://arktype.io/docs/configuration#tojsonschema)). | As with Zod's `"any"` mode, a fallback may intentionally discard constraints. Generic inference must reject schemas whose resolved output domain is unconstrained or multi-family rather than interpreting successful conversion alone as sufficient precision. |
| **Effect Schema 4** | The vendored `4.0.0-beta.102` adapter maps Effect's encoded side to Standard Schema input and decoded `Type` to output ([version](../../.repos/effect/packages/effect/package.json#L1-L5), [validation adapter](../../.repos/effect/packages/effect/src/Schema.ts#L1261-L1281)). Its Standard JSON Schema adapter likewise converts the original schema for input and `toType(self)` for output, supports only Draft 2020-12 and Draft 7, and throws for other targets ([converter](../../.repos/effect/packages/effect/src/Schema.ts#L1311-L1327), [input/output split](../../.repos/effect/packages/effect/src/Schema.ts#L1340-L1349)). | Effect confirms that validation compatibility and JSON conversion are separate adapters and that encoded/decoded transformation boundaries are material. Unsupported targets or compiler-unrepresentable semantics must remain definition failures unless explicitly mapped. |

These libraries confirm that transforms are ordinary, input and output can differ in primitive family, and conversion fidelity has explicit failure/fallback seams. Vendor-specific object internals are neither standardized nor stable enough to be a portable inference contract.

## Conservative output-shape classification

The following table separates **value-family evidence** from a complete SQL DDL choice. “Unambiguous” means every value admitted by the resolved output schema belongs to one portable logical family; it does not mean constraints or dialect representation can be generated without additional decisions.

| Resolved output JSON Schema | What is unambiguous | What still is not |
| --- | --- | --- |
| Exactly `type: "string"`, or `const`/`enum` containing only strings | Textual value family. String enum members can support a check constraint if preserved. | Bounded vs unbounded storage, collation, case behavior, char/varchar/text choice, binary decoding, UUID/date/time semantics. JSON Schema `format` is annotation-only by default, so it cannot alone justify a temporal/UUID physical type ([format rules](https://json-schema.org/draft/2020-12/json-schema-validation.html#name-format-annotation-vocabular)). |
| Exactly `type: "boolean"`, or boolean-only `const`/`enum` | Logical boolean family. | Dialect storage/encoding and default. |
| `type: [T, "null"]` or an equivalent union where every non-null branch resolves to the same unambiguous family | SQL nullability of family `T` is semantically justified. | Omission, default, and whether a null-only schema is a useful column. |
| Exactly `type: "integer"` | Values are mathematically integral. | Width, signedness, range, overflow behavior, and even JavaScript losslessness. JSON Schema numbers are unbounded and `integer` supplies no width ([numeric interoperability](https://json-schema.org/draft/2020-12/json-schema-validation.html#name-validation-of-numeric-instan)). A portable integer column is safe only if explicit bounds fit its chosen common range. |
| Exactly `type: "number"` | Numeric value family. | Floating vs exact decimal, precision, scale, and range. `multipleOf` constrains values but does not declare SQL decimal scale ([numeric keywords](https://json-schema.org/draft/2020-12/json-schema-validation.html#name-validation-keywords-for-num)). |
| Exactly `type: "array"` or `"object"` | JSON structural family. | JSON document column vs text encoding vs normalized tables; dialect JSON capabilities; query/index semantics. This requires an explicit JSON-storage policy/mapping. |
| `const` or `enum` with one non-null primitive family | That primitive family, even if `type` is absent; JSON Schema permits enum/const values of any type ([enum/const](https://json-schema.org/draft/2020-12/json-schema-validation.html#name-enum)). | The same physical choices as the inferred family. Mixed-family enums are ambiguous. |
| `$ref`, `allOf`, `anyOf`, `oneOf`, `if/then/else`, or `not` | Only what remains after complete reference resolution and semantic normalization. | Keyword presence alone says no single family. If valid branches span families, or resolution is incomplete/cyclic beyond the classifier, mapping must be explicit or rejected. |
| `{}`, `true`, absent `type`, unconstrained fallback, mixed primitive union, or conversion failure | Nothing sufficiently narrow for a scalar SQL type. | Requires explicit mapping or a definition error. `false`/unsatisfiable schemas should be a definition error because no persisted value can validate. |
| Non-JSON output (Date, BigInt, bytes/classes, Map/Set, symbol/function, `undefined` as a value) | Nothing through Standard JSON Schema unless the author supplies a serialization representation. | Requires an explicit codec/storage mapping; if none exists, definition error. |

A classifier must operate on the full resolved semantic schema, not just read the root `type`: references and applicators can narrow, widen, or make a schema unsatisfiable. Conversely, annotations such as `title`, `description`, `examples`, and `default` must not affect physical type inference; the JSON Schema specification defines `default` as associated metadata, not insertion behavior ([metadata vocabulary](https://json-schema.org/draft/2020-12/json-schema-validation.html#name-default)).

## Design implications for later decision tickets

1. Treat Standard Schema validation and storage reflection as separate capabilities. Accepting a `FieldSchema` does not prove that SQL DDL can be inferred.
2. If JSON Schema participates, request and classify the **output** schema for the selected/persisted representation. Input schema remains useful for API validation but is not column evidence.
3. Keep omission, SQL nullability, and database defaults distinct. `undefined`/optional means field absence in the current Store type construction ([optional output keys](../../packages/store/src/record.ts#L89-L105)); JSON `null` is a stored value; JSON Schema `default` is annotation.
4. Make conservative inference monotonic: text and logical boolean families are clear; nullable variants are clear after semantic union normalization; numeric, temporal, binary, structural JSON, mixed unions, and unconstrained outputs need explicit decisions unless later tickets define and justify a bounded portable policy.
5. Conversion throw, unsupported target, unresolved reference, unconstrained fallback, non-JSON output, ambiguous family, and unsatisfiable output should surface as definition-time failures unless an explicit mapping supplies the missing storage contract.
6. Current Core validators need added source-owned storage evidence somewhere outside their opaque Standard Schema runtime surface. Do not infer them by vendor name, private function identity, or sample validation probes.
7. Preserve operation-specific schemas: create/update may transform caller input, while select describes what is read from storage. Any mapping must guarantee all successful write outputs round-trip through select, matching the Store's existing type-level constraint.

These implications identify required evidence and error boundaries without selecting the eventual Commissary API, metadata shape, inference algorithm, or dialect-specific column builders.
