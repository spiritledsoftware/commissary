# Run-settlement hooks

Reference snapshots: Flue `b814b82b2`; pi-mono `027a58479`; Hermes Agent `097f0d016`; OpenCode `a45c2b917`; TanStack AI `1120f0f88`; Cloudflare Agents `413011e5b`; Vercel AI SDK `2ab3f346a`; Effect AI `9867b9fc6`. Paths and line numbers are relative to this repository.

“Replace” below means changing the candidate result before the caller observes successful settlement. None of the inspected systems exposes a callback that mutates a result **after** it is durably or publicly settled. An awaited callback may delay a return without thereby making an already-persisted turn nonterminal.

## Observed distinctions

- **Quality gates run before settlement.** Flue `useAgentFinish`, Hermes `pre_verify`, pi-mono’s queued work after `agent_end`, TanStack `onShouldContinue`, Vercel `stopWhen`, and Cloudflare recovery decisions all operate before a run is allowed to become terminal (or while repairing an interrupted run). They do not edit an already-settled result.
- **Candidate transforms are also pre-settlement.** Hermes `transform_llm_output`, pi-mono `message_end`, OpenCode `experimental.text.complete`, TanStack structured validation, and Vercel output parsing determine the value that will settle. Their existence must not be described as post-settlement mutation.
- **“Post-finish” has two meanings.** pi-mono `agent_settled` and OpenCode’s detached idle event are genuinely observational. Flue `useResponseFinish`, TanStack/Vercel finish callbacks, and Hermes `on_session_end` are logically terminal observers but remain on the awaited return path; they can delay outward settlement even though they cannot change the result. Cloudflare is the opposite edge case: `onChatResponse` is awaited by the enclosing call, but durable message settlement and lock release precede it.
- **No framework makes arbitrary callbacks safe by default.** Turn-count/recovery budgets stop repeated continuations, not a callback that never resolves. Where hooks are awaited, a hook-local timeout or cooperative cancellation is absent in the inspected APIs.

## Commissary decision

Commissary separates four phases: a bounded pre-settlement gate that returns `settle | continue`, candidate-result transformation at the Model and Tool seams, atomic settlement, and a read-only post-settlement observer. A continuation adds a durable instruction and increments a durable count before the Runtime re-enters the default Machine or custom Loop under the same Run and active Execution Claim. Core allows at most 32 continuation Steps; at the ceiling, it saves the current candidate result. Each Settlement Gate handler has a 30-second deadline. A timeout produces a Hook Error Event and is treated as accepting the candidate, after which the remaining handlers run. No Hook can rewrite or reopen an already settled Run.

## Common patterns

1. **Continuation is a new turn, not a retroactive edit.** Systems that enforce quality append an instruction or permit another tool-result/model iteration.
2. **Final-result replacement happens before the terminal record/return.** Same-role or typed-result constraints keep replacement explicit; post-finish callback return values are ignored.
3. **Budgets count repeated work, while timeouts bound wall clock.** Robust systems use both and persist recovery counters; neither substitutes for a timeout around an arbitrary callback.
4. **Durable recovery is a separate state machine.** Cloudflare and Flue persist enough intent/counters to resume or terminalize after restart; ordinary in-process finish observers do not provide recovery semantics.
5. **A settled observer should be detached.** OpenCode’s idle event demonstrates the non-blocking shape. Awaited “finish” observers in several systems can still delay API/generator completion despite being unable to alter the result.
